# MegaMail implementation batches

## Build policy

User instruction: start the prioritized work and build only after a large batch of patches.

- All implementation owners prepare source and regression tests without Cargo or helper compilation.
- Parent owns core module declarations, dependency manifests, lockfiles, serial UI integration, and the build slot.
- Freeze the whole batch before integration. No agent may continue changing a frozen file while validation runs.
- Run one grouped verification window per large batch. Core and native are independent packages; execute their necessary build/test commands serially in that window, not after individual patches.
- Do not set CARGO_TARGET_DIR or RUSTC_WRAPPER.
- Formatting and synthetic Python/Node checks may run during patch preparation.
- Report failed validation honestly. Necessary corrections receive a bounded follow-up verification window, not a false green claim.
- Build success, synthetic regression success, native UI acceptance, real-provider operation, and measured performance are separate gates.

## Evaluation rules

- “Implemented” requires a production call path. “Prepared module” requires integration; it is not a shipped native feature.
- “Tested” names the executed command, test surface, and exclusions.
- A latency improvement needs before/after measurements at the same seam. Injected JS/API stalls are not IMAP round trips or native first paint.
- Queued is not accepted, sent, or delivered. Ambiguous acceptance must not enter automatic retry.
- Missing app-owned provider registrations are a release blocker; do not invent IDs or reuse Thunderbird's identity.
- No live provider calls, real mail mutations, credentials, private profiles, or unsolicited account migration are authorized by these tasks.
- All report and fixture data must be synthetic.
