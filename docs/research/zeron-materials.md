# Zeron effects and rendering

This note covers the window materials, rendering effects, and frame-cost controls that shape Zeron's appearance. It leaves the color tokens and task hierarchy to the companion design and hierarchy research.

The main visual fact is that Zeron's marketing-screen glass comes from the desktop compositor. On macOS, GPUI installs a native behind-window blur and Zeron paints translucent shell colors over it. On Linux, Zeron keeps those visible shell colors opaque: the only window transparency is for custom-decorated corner cutouts. Its floating in-app frosted cards use a separate blur path supplied by Zeron's GPUI fork. These are distinct effects; the pinned GPUI Kit stack can reproduce the opaque shell, window transparency/material modes, and custom titlebar without extra renderer work, while exact in-app backdrop blur needs additional renderer support.

## The three material paths

| Surface | Zeron implementation | What the pinned GPUI Kit can do | MegaMail consequence |
| --- | --- | --- | --- |
| Whole window over the desktop | `WindowBackgroundAppearance::Blurred` on glass themes; translucent theme fill; native AppKit behind-window material on macOS. | Kit re-exports GPUI's `Window` and `WindowOptions`. GPUI has `Opaque`, `Transparent`, and `Blurred` window modes, but its API says native backdrop blur is not always supported. Linux alpha is available; native window blur depends on the compositor. | Keep content surfaces opaque on Linux. `Transparent` may still be used with client-side decorations so only the rounded corner cutouts show the desktop. Do not lower the whole window alpha and expose arbitrary wallpaper behind mail text. |
| Floating card over content inside the app | Zeron's `frosted` element snapshots and blurs the scene under a popover/composer, then paints shadow, tint, border, and contents in one layer. | The stock `gpui-pre 0.3.8` source pinned by Kit has no `Window::paint_backdrop_blur` API. Kit can draw the tint, border, shadow, and rounded card; exact scene blur needs a renderer or backend that supplies that primitive. | Start with the same card geometry and a solid/tinted fill. Add scene blur only if a measured product review says the card cannot read well without it. |
| Content fading into a glass edge | Zeron uses GPUI-fork `EdgeFade` so each painted primitive fades at the scroll boundary. A gradient overlay cannot fade into desktop pixels that are behind the native window and outside GPUI's scene. | Stock Kit can use ordinary GPUI drawing and gradients over a known, opaque app surface; it has no fork's per-primitive `EdgeFade`. | With the opaque Linux shell, use a small gradient over the known shell color if the design needs it. True fade-through-glass belongs with the optional renderer work. |

Zeron's source makes the platform split explicit: both glass alpha constants resolve to `0.80` on macOS/Windows and `1.0` elsewhere; `is_glass` controls desktop translucency, while `is_frost` controls local scene blur and includes Linux. The starting glass tint is raised as needed to preserve primary and muted text contrast over the worst-case desktop luminance, so the shell is not simply a fixed-alpha sheet ([`theme.rs`, lines 785–928](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/crates/ui/src/theme.rs#L785-L928)). The window background is `Transparent` on Linux for alpha compositing and corners; on other platforms it is `Blurred` only when the selected surface is glass ([`theme.rs`, lines 1113–1138](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/crates/ui/src/theme.rs#L1113-L1138)). The app applies that mode when it creates the window and reapplies it after theme changes, because the macOS blur view is removed when the mode changes away from `Blurred` ([`lib.rs`, lines 400–463](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/crates/ui/src/lib.rs#L400-L463), [`appearance.rs`, lines 341–363](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/crates/ui/src/appearance.rs#L341-L363)).

The macOS backend implements that mode with `NSWindow` transparency and an `NSVisualEffectView` using `UnderWindowBackground` material and `BehindWindow` blending ([ZUI backend at the revision Zeron pins, lines 1664–1710 and 3414–3429](https://github.com/zeronsh/zui/blob/dce5c1f737a834b32c2b531d552ea78035e54093/crates/gpui_macos/src/window.rs#L1664-L1710)). That is the reason the marketing screenshot can sample wallpaper behind the app while retaining a controlled, theme-colored shell.

GPUI Kit 0.7.1 pins the default GPUI backend to `gpui-pre 0.3.8` ([Kit manifest, lines 63–82](https://github.com/longbridge/gpui-kit/blob/288767cc730ca4977852a7860f52a8465a61876f/Cargo.toml#L63-L82)); its root re-exports GPUI, so the window mode and normal paint APIs are usable without a second GPUI dependency ([Kit root, lines 1–14 and 100–103](https://github.com/longbridge/gpui-kit/blob/288767cc730ca4977852a7860f52a8465a61876f/crates/kit/src/lib.rs#L1-L14)). The `WindowBackgroundAppearance` enum documents `Blurred` as “not always supported” (`gpui-pre 0.3.8`, `src/platform.rs:2710–2732`). In that pinned Linux backend, Wayland binds the KDE blur protocol optionally (`gpui-pre-linux 0.3.8`, `src/linux/wayland/client.rs:256, 306`) and requests blur only when that protocol is present (`src/linux/wayland/window.rs:2272–2286`); X11's backend only switches the renderer's transparency flag (`src/linux/x11/window.rs:297–307`). Thus a `Blurred` setting is not a portable Linux material.

Zeron's in-app frost is different from the native window blur. Its wrapper calls `window.paint_backdrop_blur` inside one scene layer ([`frost.rs`, lines 1–9 and 72–94](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/crates/ui/src/frost.rs#L1-L94)); the fork defines the blur API in `gpui/src/window.rs:4091` and edge-fade scope in `gpui/src/window.rs:3525`. The Linux blur implementation is a Zeron WGPU port. These methods do not exist in the stock `gpui-pre 0.3.8` source used by Kit. Zeron's dependency comment inventories the rest of that renderer delta: bounded blur scratch and Gaussian kernels, per-primitive edge fades, transparent-window alpha fixes, and image atlas eviction ([Zeron manifest, lines 65–98](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/Cargo.toml#L65-L98)). Pulling that fork in is a GPUI backend and version-integration project, not adding one small UI helper.

## Window chrome and corner treatment

Kit already supplies a custom `TitleBar` and its matching `TitleBar::window_options()` for app-owned titlebar dragging ([`title_bar.rs`, lines 59–92](https://github.com/longbridge/gpui-kit/blob/288767cc730ca4977852a7860f52a8465a61876f/crates/component/src/title_bar.rs#L59-L92)). The Dock example demonstrates a Linux client-decorated transparent window on that base ([`dock/main.rs`, lines 426–439](https://github.com/longbridge/gpui-kit/blob/288767cc730ca4977852a7860f52a8465a61876f/examples/dock/src/main.rs#L426-L439)). Kit's `window_border()` already draws Linux client-side shadow, borders, and resize hit zones; its default shadow inset is 20px ([`window_border.rs`, lines 11–30 and 130–155](https://github.com/longbridge/gpui-kit/blob/288767cc730ca4977852a7860f52a8465a61876f/crates/component/src/window_border.rs#L11-L30)).

One limitation matters for a rounded floating shell: Kit deliberately sets that generic frame's radius to zero because GPUI clips child content to a rectangular mask and rounded frame corners would leave children visible in the corners ([same file, lines 19–22](https://github.com/longbridge/gpui-kit/blob/288767cc730ca4977852a7860f52a8465a61876f/crates/component/src/window_border.rs#L19-L22)). Zeron solves its side of this by rounding each full-bleed chrome layer at the Linux floating-window edges, switching back to square for tiled/maximized windows ([`shell.rs`, lines 6849–6888](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/crates/ui/src/shell.rs#L6849-L6888)). MegaMail can follow that app-level pattern without changing GPUI, but must treat each background-filling root layer consistently; rounding only the outer frame is insufficient.

## Why the effects stay responsive

The blur code is scoped and bounded rather than painted as an always-on full-window filter. `frosted` paints the blur and card contents in a single layer to keep draw order stable. Zeron's performance notes say the WGPU path reuses normalized Gaussian weights and scissors passes to the needed pixels; they also report CPU and memory reductions for one Linux software-Vulkan workload. That historical profile is dated 2026-09-05 and compares app revisions from v0.2.37; it uses a synthetic chat, Xvfb, and a software adapter, so it is evidence for the techniques, not a performance forecast for MegaMail or a physical GPU ([profile, lines 1–10, 12–38, and 107–118](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/docs/performance-resource-usage.md#L1-L38)).

Other useful patterns do not require that renderer fork:

- The GPUI cached-view API reuses a rendered subtree until its entity, bounds, or text style changes (`gpui-pre 0.3.8`, `src/view.rs:233–244`). Zeron applies it to its sidebar pane ([`shell.rs`, lines 6994–7010](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/crates/ui/src/shell.rs#L6994-L7010)). For MegaMail, cache stable navigation or list chrome and invalidate it on real state changes; do not rebuild all message rows for a hover.
- Zeron drives decorative fades at 30 Hz and chunky loader pulses at 15 Hz, uses short-lived leases, and schedules nothing when no spinner is mounted ([`motion.rs`, lines 49–127](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/crates/ui/src/motion.rs#L49-L127)). Keep animations short, local, and reduced-motion aware; continuous decorative animation works against idle efficiency.
- Zeron's image path bounds raster dimensions and decode allocation, reuses a matching SVG raster, and keeps a current lower-resolution image when a larger one would exceed the available cache budget ([`image_media.rs`, lines 28–45, 97–133, 257–305](https://github.com/zeronsh/zeron/blob/037f4c10d67a38175b2386e776aba54355b4e941/crates/ui/src/image_media.rs#L28-L45)). This is directly relevant to email attachments and thumbnails; decoding belongs off the UI thread.

## MegaMail implementation and measurement gates

1. Build the first Linux shell with Kit's `TitleBar`, `WindowOptions`, client-side decorations, and `window_border()`. Keep the list, reading pane, and toolbar fills fully opaque. Use a transparent native window only when required to reveal the CSD corner cutouts; round every background-filling corner layer when the window floats, and square them when tiled. This preserves the Zeron spacing, typography, quiet borders, and layout while removing wallpaper/compositor variance from text contrast.
2. Capture and compare the same 1280×800 mail fixture on GNOME Wayland, KDE Wayland, and X11. Include floating, tiled, maximized, light/dark, scrolling, hover, and modal states. The screenshot must show no desktop leaking through readable content, and window edges and resize hit areas must remain correct after tiling changes.
3. Record a release-build baseline before any local blur work: idle redraw/CPU, inbox open and search latency, scroll frame-time percentiles on a large message list, and GPU/RSS after opening and closing image previews. Repeat on each supported Linux path and a real GPU; don't transfer Zeron's Xvfb/software-Vulkan numbers to hardware.
4. Consider a custom GPUI renderer only if an opaque prototype fails a concrete visual requirement and the baseline shows enough frame and memory headroom. For a blur prototype, restrict blur to a visible card-sized region and measure it while scrolling, resizing, and opening previews; reject it if idle frames continue, frame-time tails regress, or GPU memory grows with repeated open/close cycles. Keep the Linux opaque rendering as the stable fallback.

That is the faithful Linux-first reading of Zeron: copy its surface geometry and hierarchy from the design references, give the foreground a dependable opaque base, and make compositor-dependent glass an optional platform material. The macOS hero is the example to understand the effect, not the baseline MegaMail must reproduce.
