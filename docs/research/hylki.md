# Hylki source audit for MegaMail

Audited checkout: `main` at `43f2d4665f01a1f0ef4474d719179b8e5b61471c`; package version `1.42.0`. This is a source-only review. No build or tests were run.

## What the repo gives us

Hylki is a mature Linux email client, with IMAP, POP3, JMAP and Microsoft Graph; OAuth; background sync; a local SQLite cache; MIME parsing; SMTP/JMAP submission; drafts and an Outbox; threading; attachments; sender checks; OpenPGP; and privacy controls. The product scope is visible in [HYLKI_UPSTREAM_README.md:40-55](../HYLKI_UPSTREAM_README.md#L40) and its implementation is spread through the modules below.

The useful distinction for MegaMail is that Hylki contains a lot of valuable mail behavior, but does not expose it as a reusable mail library. `Cargo.toml` declares one package and `src/main.rs` declares private modules and starts a Relm4 application; there is no `src/lib.rs` target. See [Cargo.toml:1-8](../../Cargo.toml#L1) and [src/main.rs:3-55](../../src/main.rs#L3). A GPUI app cannot depend on Hylki as a crate without first creating a library boundary or moving code into a new core crate.

`backend.rs` is easy to misread as the live abstraction. Its `MailBackend` trait exposes only `accounts`, `folders` and `messages`, and its implementation is `MockBackend` for the offline showcase; real protocol sessions are owned by `worker.rs`. See [src/backend.rs:1-23](../../src/backend.rs#L1) and [src/worker.rs:1009-1027](../../src/worker.rs#L1009). It is not the seam to use for a full mail-engine extraction.

## Optional standalone source modules

Only two Rust modules are standalone at this revision: `src/mutf7.rs` implements IMAP modified UTF-7 without GTK or `crate::` references, and `src/rng.rs` wraps the operating-system CSPRNG without GTK or `crate::` references. The source scan found no other module meeting both conditions. Their APIs are small and their in-file tests travel with the modules: [src/mutf7.rs:1-20](../../src/mutf7.rs#L1), [src/mutf7.rs:88-124](../../src/mutf7.rs#L88), [src/rng.rs:1-11](../../src/rng.rs#L1), [src/rng.rs:22-57](../../src/rng.rs#L22). Include either only when MegaMail implements the corresponding IMAP mailbox-name or security-token behavior; a visual preview has no reason to pull them in.

If both behaviors are needed, a new `apps/megamail/src/main.rs` can include the modules directly while Hylki remains untouched; include only the one needed when implementing one behavior:

```rust
#[path = "../../../src/mutf7.rs"]
mod hylki_mutf7;
#[path = "../../../src/rng.rs"]
mod hylki_rng;
```

The new package would need direct dependencies on `base64 = "0.22"` for `mutf7.rs` and `getrandom = "0.2"` for `rng.rs`; Rust requires direct dependencies even if GPUI or another dependency also uses them. This is optional source reuse for two utilities, not reuse of Hylki's mail engine.

`percent.rs` is close but not clean: its encoder calls `gtk::glib::Uri` ([src/percent.rs:1-18](../../src/percent.rs#L1)). `models.rs` is not a pure domain module: it imports Hylki gettext helpers and calls `gtk::glib::format_size` ([src/models.rs:1-3](../../src/models.rs#L1), [src/models.rs:978-980](../../src/models.rs#L978)); several values are UI-shaped, including translated folder labels and the account accent string. `config.rs` combines serializable network accounts with UI preferences and filesystem/keyring policy. Directly including these files would pull in Hylki's crate graph rather than create a GPUI-ready core.

## Mail-engine boundary and extraction cost

The most workable current interface is `worker::spawn(account_id, account, emit) -> UnboundedSender<MailRequest>`. It creates a cache lane and a mail-worker thread, then reports typed `WorkerEvent`s to a caller-provided callback. See [src/worker.rs:742-787](../../src/worker.rs#L742). `AppModel::spawn_worker` adapts those events into Relm4 inputs at [src/app.rs:11740-11749](../../src/app.rs#L11740); `map_event` is the large app-specific event translation at [src/app.rs:21912-21998](../../src/app.rs#L21912). A GPUI adapter can preserve the request/event semantics and send received events into GPUI's update queue.

The boundary is internal, not a stable library API. `MailRequest` and `WorkerEvent` refer to crate-local `AccountConfig` and model types ([src/worker.rs:316-318](../../src/worker.rs#L316), [src/worker.rs:580-590](../../src/worker.rs#L580)). The worker also calls Hylki config, translations, models and cache throughout the protocol paths. Direct GTK references remain even in the worker: content-type lookup uses `gtk::gio` at [src/worker.rs:3968-3969](../../src/worker.rs#L3968), and text escaping uses `gtk::glib` at [src/worker.rs:10205](../../src/worker.rs#L10205). These are small replacements, but the wider dependency graph is not.

There is a concrete module cycle to break before packaging the engine: cache migration calls worker helpers to decode subjects and clean old names ([src/cache.rs:644-674](../../src/cache.rs#L644), [src/cache.rs:676-699](../../src/cache.rs#L676)); worker parsing calls `cache::note_msgid_case` ([src/worker.rs:7989-8015](../../src/worker.rs#L7989)). In addition, Graph and JMAP use `super::*` imports from `worker.rs`, so moving them out independently will require a deliberate shared protocol/types module.

The cache is a strong thing to preserve. It is keyed by account/folder/UID, has schema upgrades, indexes message IDs and stores retry-safe MIME bytes for queued messages. It uses one SQLite connection per owner thread, WAL for concurrent readers, 0700 on the data directory and 0600 on the database and sidecars ([src/cache.rs:1-8](../../src/cache.rs#L1), [src/cache.rs:476-494](../../src/cache.rs#L476), [src/cache.rs:626-641](../../src/cache.rs#L626)). Its migration rules are part of preserving existing user data, not incidental setup.

## Performance work worth carrying forward

- Hylki gives cached bodies their own fast lane so opening already-cached mail does not queue behind network sync, and it has a separate read connection/thread for conversation summaries ([src/worker.rs:789-840](../../src/worker.rs#L789)). On startup it emits cached folders before connecting when possible ([src/worker.rs:1184-1214](../../src/worker.rs#L1184)).
- Cold sync asks for a fast first window of 200 messages and schedules the remaining folder index as background work; the backfill chunk is 1,000 rows, grouped body fetches use batches of 10, body prefetch is capped at 50 recent messages, and attachment prefetch at 25 ([src/worker.rs:39-93](../../src/worker.rs#L39), [src/worker.rs:1280-1300](../../src/worker.rs#L1280)). Older attachment bytes are fetched only on demand.
- Reader loads can overtake queued folder-list work and interrupt a background network read while restoring that job for retry ([src/worker.rs:1030-1124](../../src/worker.rs#L1030)). Preserve this user-visible priority if the actor is moved to a different async runtime.
- The message list uses `gtk::ListView` row recycling; only visible rows are built and each row binds synchronously so recycled content cannot flash stale data ([src/ui/message_row.rs:1-8](../../src/ui/message_row.rs#L1)). GPUI should keep the list virtualized and key rows with stable message identity rather than constructing a widget for every indexed message.
- Hylki avoids reloading unchanged global CSS because restyling every row costs more than the change itself ([src/ui/mod.rs:43-70](../../src/ui/mod.rs#L43)). The exact GTK mechanism will not transfer, but the principle should inform theme-token updates in the new app.

Scaling tradeoff: each enabled account gets a mail thread and a cache-lane thread; a non-POP account can also get a thread-summary reader ([src/worker.rs:745-784](../../src/worker.rs#L745), [src/worker.rs:819-841](../../src/worker.rs#L819)). Request channels are unbounded ([src/worker.rs:750](../../src/worker.rs#L750), [src/worker.rs:812-813](../../src/worker.rs#L812)). That is a practical desktop tradeoff for a handful of accounts, but MegaMail should measure thread count and queue growth before increasing background fan-out or flooding updates during bulk sync.

## Security, storage and identity risks

- Credentials use Secret Service/keyring entries; account TOML is written owner-only, excludes password serialization, and migrates legacy plaintext passwords into the keyring ([src/config.rs:13-38](../../src/config.rs#L13), [src/config.rs:318-340](../../src/config.rs#L318), [src/config.rs:697-767](../../src/config.rs#L697)). Preserve the empty-password guard in `save`; it exists to avoid wiping credentials for accounts not just edited ([src/config.rs:697-716](../../src/config.rs#L697)).
- OAuth uses PKCE S256 with fresh random verifier/state and rejects state mismatches ([src/oauth.rs:467-514](../../src/oauth.rs#L467)). The provider IDs and callback assumptions are Hylki-specific, including its Microsoft registration ([src/oauth.rs:21-67](../../src/oauth.rs#L21)); MegaMail needs its own provider app registration and redirect configuration.
- The SQLite cache contains plaintext message bodies (`bodies.body`) and attachment bytes (`attachments.data`); permissions restrict local users but do not encrypt the database ([src/cache.rs:69-95](../../src/cache.rs#L69), [src/cache.rs:488-494](../../src/cache.rs#L488)). OpenPGP plaintext and attachments are explicitly excluded from cache ([src/worker.rs:3784-3805](../../src/worker.rs#L3784)). Preserve that exclusion when adapting the cache API.
- Reader privacy is a behavior to reimplement, not just a WebKit widget detail. Remote URLs are removed while content is blocked, and a per-message CSP independently prevents remote fetches; only the user's explicit allow decision changes the resource policy ([src/ui/message_view.rs:5838-5874](../../src/ui/message_view.rs#L5838), [src/ui/message_view.rs:6655-6697](../../src/ui/message_view.rs#L6655)). Message bodies render sandboxed with scripts disabled per the security notes ([docs/SECURITY.md:39-68](../../docs/SECURITY.md#L39)). GPUI's chosen HTML renderer needs an equally explicit isolation story.
- Outgoing HTML is sanitized with `ammonia`, allowing mail-oriented markup and a constrained URL scheme set ([src/markdown.rs:1047-1076](../../src/markdown.rs#L1047)). Keep this separate from incoming-message rendering policy.
- Hylki's config/data/cache paths and keyring service name are literal `hylki`/`co.hyprlab.Hylki` values ([src/config.rs:41-57](../../src/config.rs#L41), [src/config.rs:108-117](../../src/config.rs#L108), [src/config.rs:270-271](../../src/config.rs#L270), [src/config.rs:660-663](../../src/config.rs#L660), [src/cache.rs:481-491](../../src/cache.rs#L481)). MegaMail must pick separate paths/service IDs or write a deliberate, non-destructive migration. Pointing both apps at one cache without version and ownership rules risks data loss or cross-app writes. Hylki also already has a Vireo-to-Hylki migration that should not be confused with MegaMail migration ([HYLKI_UPSTREAM_README.md:34-38](../HYLKI_UPSTREAM_README.md#L34)).

## Smallest credible implementation sequence

1. Keep the full Hylki tree and history intact. Put the new GPUI executable under `apps/megamail`; do not add unused Hylki utilities to an early UI preview. Include `mutf7.rs` or `rng.rs` by path only when the corresponding IMAP or auth behavior is implemented. This reuses source for that behavior without implying the mail engine has been ported.
2. Make a real `mail-core` boundary before building substantial UI around pretend data. Start by separating shared message/account/protocol types from `models.rs` and account/network settings from the 5k-line UI-and-app `config.rs`; replace the handful of GTK helpers and injected gettext calls with neutral helpers. Move the actual `cache.rs` and protocol worker together with their shared MIME helpers, then break the cache/worker helper cycle.
3. Preserve the `MailRequest`/`WorkerEvent` contract around the GPUI adapter. Keep Hylki's IMAP, POP3, Graph and JMAP behavior and data migrations intact unless MegaMail deliberately narrows the product scope. Do not present `backend.rs::MailBackend` as evidence that the live engine is already abstracted.
4. Port the Hylki list virtualization, cache-first startup, reader priority and bounded prefetch policy into the GPUI design. Then implement the Zeron-inspired styling in the new UI without coupling visual polish to protocol/cache code.
5. Rebuild the message-rendering isolation and auth-provider configuration before shipping: blocked remote content, script isolation, outgoing sanitization, PKCE state checks, keyring persistence and non-destructive cache namespace decisions are product requirements, not optional polish.

Immediate scope skipped: wholesale port of GNOME-only integrations and a compatibility claim for Hylki's full UI. Main risk: isolated utility reuse does not provide a mail backend; real mail-engine reuse requires the extraction in steps 2-3, beyond a GPUI shell or `MailBackend`.
